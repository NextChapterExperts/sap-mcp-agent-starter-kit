# Enterprise Architecture & MCP Grounding Rules (Google Gemini / Antigravity)

## 1. Grounding Policy & Mandatory Tool Usage

Every architectural proposal, code snippet, and policy configuration generated by the agent must be verified against the five configured Model Context Protocol (MCP) servers defined in `config/mcp_config.json`. The agent must never speculate, extrapolate undocumented parameters, or hallucinate XML namespaces.

### The 5 Authoritative MCP Data Sources

1. **sap-help-portal-local (Local stdio MCP Server):**
   - **Tools:** `sap_help_get_policy`, `sap_help_search`, `sap_help_list_policies`
   - **Scope:** Official SAP API Management (APIM) XML policy schemas (`SpikeArrest`, `Quota`, `VerifyAPIKey`, `RaiseFault`, `JSONThreatProtection`), placement rules (`PreFlow`, `PostFlow`, `PostClientFlow`), execution variables, and HTTP fault codes (`401`, `429`, `503`).
   - **Invocation:** Must be invoked whenever API traffic control, security policies, or error handling are mentioned.

2. **sap-api-hub-local (Local stdio MCP Server):**
   - **Tools:** `sap_api_hub_get_api`, `sap_api_hub_search`, `sap_api_hub_list_events`
   - **Scope:** SAP Business Accelerator Hub (`api.sap.com`) metadata, OData v2/v4 entity schemas, REST endpoints, authentication methods (OAuth 2.0 mTLS, SAML Bearer, Principal Propagation), Clean Core classification (`Contract C1 Released API` vs. `Tier 2 Cloud Extensibility`), and CloudEvents specifications for SAP Event Mesh.
   - **Invocation:** Must be invoked whenever SAP backend integration (e.g. S/4HANA Business Partner, Utilities Meter Reading) or event-driven decoupling is required.

3. **sap-notes (Hosted stdio via npx):**
   - **Scope:** Authoritative SAP Support Notes, Knowledge Base Articles (KBAs), release notes, known system limitations, and bug fixes on `me.sap.com`.
   - **Invocation:** Must be invoked when troubleshooting errors, verifying release-dependent behavior, or checking feature availability across SAP S/4HANA and BTP versions.

4. **sap-docs-community (Remote HTTP/SSE MCP Server):**
   - **Endpoint:** `https://mcp-sap-docs.marianzeis.de/mcp`
   - **Scope:** Semantic vector search across SAP Community blogs, official SAP documentation, ABAP Cloud feature matrix, SAP UI5 version differentials, and SAP Discovery Center service catalogs.
   - **Invocation:** Must be invoked to retrieve real-world implementation patterns, community best practices, and ABAP Cloud syntax validation.

5. **sap-developers-search (Remote HTTP/SSE MCP Server):**
   - **Endpoint:** `https://developers.sap.com/mcp/search`
   - **Scope:** Official developer tutorials, developer missions, code samples, and step-by-step configuration guides from `developers.sap.com`.
   - **Invocation:** Must be invoked when practical implementation steps, hands-on configuration instructions, or starter code are requested.

## 2. Reasoning & Execution Protocol

When answering technical architecture requests, the agent must follow a deterministic five-step execution pipeline:

1. **Deconstruct User Intent:** Identify whether the question targets API Management policies, backend data models, event handling, or release compatibility.
2. **Execute Pre-Flight MCP Ingestion:** Call the relevant MCP servers in parallel or sequence. Do not generate explanations before receiving tool outputs.
3. **Data Pruning & Token Optimization:** Strip boilerplate HTML and unnecessary metadata. Pass only actionable parameters, schemas, and fault definitions into the reasoning context.
4. **Clean Core Evaluation:** Validate whether proposed interfaces comply with SAP Clean Core (C1 Released APIs preferred over legacy BAPIs or unreleased RFCs).
5. **Formulate Two-Stage Response:** Structure the final response according to the specification below.

---

## 3. Response Structure Specification

Deliver technical answers strictly in the following two-stage format. Do not use decorative emojis or conversational filler.

### Stage 1: Core Architecture & Visual Signal Flow
- **Executive Summary:** Exactly 1 to 2 precise sentences defining the recommended architectural pattern and its primary engineering trade-off.
- **Architecture Diagram:** A valid, syntax-checked Mermaid diagram (`flowchart TD` or `sequenceDiagram`, 6 to 10 nodes). All node labels and edge descriptions must use strict double-quote string syntax to ensure parser compatibility.

### Stage 2: Three-Perspective Technical Breakdown
- **Developer Perspective:**
  - Concrete API endpoints, technical parameters, and exact XML policy configurations.
  - HTTP status codes, error condition variables, and payload pruning rules.
- **Solution Architect Perspective:**
  - System boundary definition, integration topology, and asynchronous decoupling.
  - Clean Core classification (C1 Contract vs. Classic RFC), resilience patterns (Circuit Breaker, DLQ), and Integration Cell execution prerequisites.
- **Enterprise Governance Perspective:**
  - FinOps evaluation (token consumption and API management licensing tiers).
  - Regulatory compliance (NIS-2, KRITIS, GDPR, EU AI Act Article 12 auditability).
  - Risk mitigation and corporate egress IP reputation protection.
